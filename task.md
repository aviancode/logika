# Техническое задание: `orbita` — встраиваемый Rust-движок workflow

## 1. Назначение

Разработать библиотеку и набор CLI-инструментов на Rust, которые позволяют
описывать, проверять, запускать и наблюдать workflow внутри произвольного
приложения. `orbita` должна стать программным, clientless-аналогом n8n: UI,
HTTP-сервер и хранилище не являются обязательной частью ядра и могут быть
подключены отдельными адаптерами.

Первый релиз ориентирован на разработчиков, которые подключают workflow к
своему сервису, desktop- или CLI-приложению. Он не ставит целью немедленно
воспроизвести редактор n8n или весь его каталог интеграций.

## 2. Цели продукта

1. **Типизированный обмен между нодами.** Некорректное соединение портов
   обнаруживается до запуска: на этапе компиляции Rust workflow либо при
   валидации сериализованного графа.
2. **Встраиваемость.** Потребитель управляет жизненным циклом runtime, хранением
   данных, сетевым сервером, UI и аутентификацией. Библиотека не открывает порт,
   не требует браузера и не навязывает БД.
3. **Расширяемость.** Ноды, триггеры и интеграции поставляются плагинами с
   manifest-файлом, SemVer, зависимостями, проверкой совместимости и подписью.
4. **Безопасная изоляция.** Код плагина по умолчанию не имеет доступа к сети,
   файловой системе, переменным окружения, секретам и процессам хоста.
5. **Языковая независимость плагинов.** Контракт плагина не зависит от Rust:
   основной путь — WebAssembly Component Model, универсальный путь — отдельный
   sidecar-процесс по открытым RPC-правилам.
6. **Производительность и предсказуемость.** Асинхронный Rust runtime, план
   выполнения без лишних копирований, ограничение параллелизма, отмена,
   backpressure и наблюдаемость.

## 3. Границы первого релиза

### Входит в MVP (`0.1`)

- Описание workflow как ориентированного графа нод с именованными входными и
  выходными портами.
- Последовательное, параллельное и условное исполнение; fan-out/fan-in;
  повторные попытки, timeout и отмена запуска.
- Триггеры запуска вручную из API и программно из приложения.
- Реестр нод, загрузка плагинов, разрешение их зависимостей и lock-файл.
- Статическая проверка связей в Rust API и runtime-проверка схем для workflow из
  JSON/YAML.
- Плагины WASM и sidecar-плагины; capability-based доступ к ресурсам.
- Хранилище состояния через trait с `in-memory` реализацией; постоянное
  хранилище предоставляет приложение или отдельный адаптер.
- Секреты через абстракцию хоста; журнал запусков, структурированные логи и
  OpenTelemetry tracing.
- CLI для проверки workflow, управления плагинами и локального запуска.

### Не входит в MVP

- Визуальный редактор, собственный SaaS, multi-tenant-панель и scheduler как
  обязательные компоненты.
- Полная совместимость с экспортами, JavaScript-кодом и внутренним API n8n.
- Распределённый exactly-once runtime, распределённые транзакции и гарантии
  выполнения внешних HTTP-операций ровно один раз.
- Загрузка произвольных нативных `.dll`/`.so` в процесс хоста.

## 4. Принципиальные решения

### 4.1. Два уровня типизации

Нельзя обеспечить compile-time Rust-типы для плагина, написанного на любом
языке. Поэтому использовать два совместимых слоя:

| Уровень | Где применяется | Гарантия |
| --- | --- | --- |
| Rust API | Workflow собран кодом на Rust | Ошибка несовместимых портов при компиляции |
| Canonical Schema | Workflow из файла и межъязыковые плагины | Проверка до запуска и на границе плагина |

Каждый порт имеет `TypeRef`: стабильное имя типа, версию схемы, каноническое
представление и fingerprint (SHA-256). Схемы описывают примитивы, `struct`,
`enum`, массивы, `map`, optional-поля и tagged union. Для сериализации на
границе плагинов применяется согласованный бинарный формат (например, MessagePack
или CBOR); JSON используется только для удобочитаемых manifest и workflow.

`orbita` обязана проверять:

- существование ноды и порта;
- совпадение или объявленную совместимость `TypeRef`;
- обязательность входов, кратность соединений и отсутствие циклов без явной
  control-flow-ноды;
- совместимость версий схем при обновлении плагина;
- фактический payload на входе/выходе недоверенного плагина.

### 4.2. Модель workflow

Workflow — переносимый документ, не содержащий клиентских данных:

```yaml
apiVersion: orbita.dev/v1
kind: Workflow
metadata:
  name: enrich-order
  version: 1.0.0
spec:
  inputs:
    order: acme.order@1
  nodes:
    - id: validate
      uses: acme.validation/order@^1.2
      with: { strict: true }
    - id: enrich
      uses: acme.crm/enrich-customer@^2.0
  edges:
    - from: $inputs.order
      to: validate.order
    - from: validate.valid_order
      to: enrich.order
  outputs:
    enriched_order: enrich.order
```

Внутренне документ компилируется в неизменяемый `ExecutionPlan`: разрешённые
версии нод, проверенные типы, предвычисленный порядок зависимостей и политика
повторов. План кэшируется по хешу workflow и lock-файла.

Публичный Rust API должен позволять как минимум:

```rust
let engine = Engine::builder().registry(registry).store(store).build()?;
let plan = engine.compile(workflow, &lockfile)?;
let result = engine.run(plan, input, RunOptions::default()).await?;
```

Для Rust-ноды предусмотреть trait наподобие `Node`, где `Input` и `Output`
реализуют `Schema`; builder workflow не должен позволять соединить
`Output<A>` с `Input<B>`, если `A` и `B` несовместимы.

### 4.3. Исполнение

- Runtime основан на `tokio`; CPU-bound работа выносится в контролируемый пул.
- Запуск (`Run`) имеет неизменяемые `run_id`, `workflow_version`, `plan_hash`,
  `started_at`, статус и correlation ID.
- Нода получает `NodeContext`: cancellation token, deadline, trace context,
  logger, capability handles и метаданные запуска. Она не получает глобальный
  доступ к процессу.
- Семантика по умолчанию — **at-least-once** для persistable workflow. Каждая
  нода обязана объявить idempotency; для внешних эффектов поддержать
  idempotency key вида `run_id/node_id/attempt`.
- Retry-политика: число попыток, экспоненциальная задержка с jitter, набор
  retriable-кодов, timeout на попытку и общий deadline Run.
- Параллельные независимые ноды ограничиваются глобальным и per-workflow
  semaphore. Очереди имеют лимит; переполнение создаёт явную ошибку, а не
  неограниченно расходует память.
- Для циклов и пакетной обработки применяются встроенные control-flow-ноды
  (`if`, `switch`, `foreach`, `join`, `delay`). Произвольный цикл в графе
  запрещён.

## 5. Архитектура workspace

Перевести репозиторий в Cargo workspace. Внешние crate должны иметь префикс
`orbita-`; `orbita` остаётся удобным facade crate.

| Crate | Ответственность |
| --- | --- |
| `orbita` | Facade: экспорт стабильного embedded API и feature-флагов |
| `orbita-core` | Идентификаторы, схемы, порты, ошибки, manifest-модели, базовые traits |
| `orbita-workflow` | JSON/YAML-модель workflow, миграции формата, валидация, компиляция плана |
| `orbita-runtime` | Scheduler, Run, retry, cancellation, ресурсы, исполнение плана |
| `orbita-sdk` | Rust SDK для авторов нод и derive/macro для `Schema` |
| `orbita-plugin-api` | WIT-интерфейсы, общие RPC-типы, ABI-совместимость |
| `orbita-plugin-host` | Загрузка и sandbox WASM-компонентов, sidecar supervisor |
| `orbita-registry` | Индекс пакетов, SemVer resolver, trust policy, подписи, lock-файл |
| `orbita-store` | Trait персистентности и in-memory реализация |
| `orbita-cli` | `validate`, `run`, `plugin install/list/verify`, `lock` |
| `orbita-testkit` | Фиктивный runtime, тестовые ноды, contract-test для плагинов |

Все интеграции (`HTTP`, cron, PostgreSQL, очереди, UI) должны находиться в
отдельных crate или плагинах и включаться feature-флагами. `orbita-core` не
должен зависеть от web-framework, базы данных, WASM runtime или CLI.

## 6. Контракт плагинов

### 6.1. Формат пакета

Плагин распространяется как архив `.orb`:

```text
plugin.orbita.toml
plugin.wasm                 # для WASM-плагина
sidecar/…                   # либо executable и его зависимости
schemas/*.json
SIGNATURE                   # необязательно, но обязательно в strict policy
```

Минимальный `plugin.orbita.toml`:

```toml
[plugin]
id = "acme.crm"
version = "2.1.0"
api = "^1.0"
kind = "wasm-component" # или "sidecar"
license = "MIT"

[compatibility]
host = ">=0.1, <0.2"

[[nodes]]
id = "enrich-customer"
version = "2.1.0"
input_schema = "schemas/enrich-input.json"
output_schema = "schemas/enrich-output.json"

[capabilities]
network = ["https://api.example.com"]
secrets = ["crm-api-token"]
filesystem = []
```

Идентификатор плагина и ноды неизменяемы после публикации. Обновления следуют
SemVer: breaking-изменения схемы, портов или поведения требуют major-версии.
Каждая установка фиксируется в `orbita.lock` с версией, digest артефакта,
публичным ключом издателя и разрешёнными зависимостями.

### 6.2. Межъязыковой ABI

1. Основной контракт описывается в WIT и поставляется с репозиторием.
2. WASM-плагин экспортирует метаданные нод и операцию `execute`; хост передаёт
   только валидированные данные, context и разрешённые capability handles.
3. Для языка без WASM Component binding поддерживается sidecar: отдельный
   процесс, протокол versioned RPC по stdin/stdout с length-prefixed кадрами.
   В контракт включить handshake, запрос выполнения, поток логов, отмену,
   healthcheck и нормализованные ошибки.
4. Формат payload, WIT и RPC должны быть опубликованной спецификацией и иметь
   golden/contract-тесты. SDK на Rust — лишь одна из реализаций контракта.

Фраза «любые языки» означает языки, в которых можно реализовать WASM ABI или
запустить отдельный процесс. Это технически честная граница: исполнять
произвольный исходный код внутри хоста без рантайма/компилятора невозможно и
небезопасно.

## 7. Безопасность

- WASM исполняется через Component Model/WASI runtime с deny-by-default
  capability policy. Не предоставлять preopened directories, сеть, clocks,
  random, environment или сокеты без явного разрешения.
- Sidecar запускается с отдельным пользователем/песочницей ОС, лимитами CPU,
  памяти, времени, числа процессов и ограниченным набором файлов. На Windows
  использовать Job Objects; на Linux — cgroups/namespaces или интеграцию с
  контейнерным runtime.
- Секреты не сериализуются в workflow, plan, логи и состояние Run. Нода получает
  одноразовый opaque handle; чтение секрета фиксируется в audit log.
- До установки проверяются SHA-256, подпись издателя и цепочка доверия.
  Production policy по умолчанию требует подписи; development policy может
  разрешать локальные неподписанные пакеты с явным предупреждением.
- Manifest проверяется до загрузки бинарника: допустимые capabilities, URL
  allowlist, API-версия, размер пакета и отсутствие path traversal в архиве.
- Redaction применяется к ошибкам, логам и trace attributes по правилам
  `Secret`/PII-полей схемы.

## 8. Хранение и публичные расширения

Определить минимальные object-safe traits: `RunStore`, `PluginStore`,
`SecretProvider`, `Clock`, `NodeExecutor` и `EventSink`. Они позволяют
подменять инфраструктуру приложения, не форкая ядро.

`RunStore` сохраняет определения workflow, скомпилированные версии планов,
запуски, попытки нод, входы/выходы (с политикой retention), события и
checkpoint. Ядро предоставляет только in-memory реализацию; постоянное
хранилище и очереди остаются зоной ответственности приложения либо отдельных
адаптеров после стабилизации trait.

В схеме БД нужны уникальные ключи `(run_id, node_id, attempt)`, миграции и
атомарная фиксация перехода статуса. При восстановлении после сбоя runtime
возобновляет только ноды, которые не были подтверждены как завершённые.

## 9. Наблюдаемость и ошибки

- Для каждого Run и каждого выполнения ноды создавать tracing span с
  `run_id`, `workflow`, `node_id`, `plugin`, `attempt`, длительностью и
  результатом — без секретов и payload по умолчанию.
- Экспорт метрик: активные Run, очередь, длительность нод, retry, timeout,
  отмены, ошибки по типам, загрузка плагинов и sandbox violations.
- Публичные ошибки должны быть классифицированы: `Validation`, `Resolution`,
  `Schema`, `Plugin`, `CapabilityDenied`, `Timeout`, `Cancelled`, `Storage`,
  `UserNode`. Ошибки плагина передаются с безопасным кодом и диагностикой.
- В CLI доступен JSON-формат вывода для автоматизированных интеграций.

## 10. Требования к качеству

- Поддерживаемые платформы MVP: Windows x86_64 и Linux x86_64. Поведение
  sandbox должно быть покрыто платформенными тестами; невозможность применить
  изоляцию — ошибка, а не тихое ослабление защиты.
- Публичный API помечен `#[non_exhaustive]` там, где планируется эволюция.
- `unsafe` запрещён в собственном коде, кроме изолированных и обоснованных
  адаптеров; lint `unsafe_code = "forbid"` включён в core-crate.
- Перед релизом выполняются `fmt --check`, `clippy -D warnings`,
  unit/integration tests, WASM/sidecar contract tests, tests миграций и
  проверка минимального набора feature-флагов.
- Не менее 80% покрытия для детерминированных модулей `core`, `workflow`,
  `registry` и `runtime`; критические ветви security policy покрываются
  отдельными негативными тестами.
- Для benchmark-набора зафиксировать baseline: компиляция графа из 100 нод,
  1 000 коротких Run и fan-out на 100 параллельных нод. Регрессия более 10%
  блокирует merge без зафиксированного обоснования.

## 11. Этапы реализации

1. **Каркас (0.1.0).** Cargo workspace, правила API/ошибок, `Schema`,
   модель workflow, валидатор графа, in-memory registry/store, unit-тесты.
2. **Runtime (0.2.0).** `ExecutionPlan`, асинхронное DAG-исполнение, timeout,
   retry, cancellation, `tracing`, примеры Rust-нод.
3. **Персистентность (0.3.0).** Контракт `RunStore`, checkpoint и
   восстановление незавершённых запусков; тестовый persistent adapter без
   добавления драйвера БД в зависимости ядра.
4. **Плагины (0.4.0).** Manifest, SemVer resolver, `orbita.lock`, WIT,
   WASM-host, capability policy, contract-test kit.
5. **Универсальные плагины (0.5.0).** Sidecar supervisor, versioned RPC,
   resource limits, SDK-образцы минимум для Python и Go.
6. **Стабилизация (1.0.0).** Security audit, benchmark, compatibility policy
   и стабильный public API.

## 12. Критерии приёмки MVP

1. Потребитель добавляет `orbita` как зависимость, создаёт runtime без запуска
   сервера и выполняет workflow через Rust API.
2. Соединение несовместимых типов отклоняется Rust builder-ом на компиляции либо
   валидатором YAML/JSON до выполнения; сообщение содержит ноду, порт и типы.
3. Граф из параллельных нод выполняется конкурентно, соблюдает лимит и корректно
   отменяется; retry не превышает объявленную политику.
4. Плагин с неподходящей версией API, повреждённым digest, недоверенной подписью
   или лишней capability не загружается.
5. Непривилегированный WASM-плагин не может прочитать файл хоста, получить
   secret или открыть сетевое соединение. Нарушение отражается в audit log.
6. Одинаковая тестовая нода запускается как WASM и как sidecar; оба пути проходят
   один набор contract-тестов и возвращают эквивалентный payload.
7. После аварийного завершения процесса persistable Run восстанавливается без
   повторного выполнения подтверждённой ноды.
8. `orbita validate workflow.yaml` и `orbita run workflow.yaml --input input.json`
   выполняются локально и возвращают машиночитаемые ошибки.

## 13. Первые артефакты после утверждения ТЗ

- Rust workspace с пустыми crate.
- Три reference-ноды: `core.if`, `core.foreach`, `http.request` (последняя —
  только как плагин с явно выданной network capability).
